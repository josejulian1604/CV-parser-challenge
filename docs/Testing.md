# Testing

## Two different things, don't conflate them
1. **Unit/E2E tests** (`tests/`) — verify code correctness. Standard
   software testing.
2. **Eval harness** (`eval/`) — measures extraction *quality* against
   a golden set. Not a pass/fail test suite; produces metrics (field
   accuracy, latency, cost) that inform design decisions and go in
   the README as evidence, not just claims.
They serve different purposes and should not be merged into one system.

## Unit tests (Vitest)
- Every module in `lib/extraction/**` gets a matching file in
  `tests/unit/**`, mirroring the path exactly
  (`grounding/match.ts` → `tests/unit/grounding/match.test.ts`).
- A stage is not "done" in PLAN.md until its test file exists — this
  is a gate, not a follow-up task to circle back to.
- Prioritize tests for deterministic, high-value logic: grounding
  match levels, offset mapping, date normalization, the fallback
  regexes, schema validation edge cases. Don't write tests that just
  mock the LLM call and assert it was called — low value.

## E2E tests (Playwright)
1-2 flows maximum, given the timeline: (a) upload a real PDF → see
extracted data rendered, (b) trigger an error state (oversized file
or unsupported format) → see the correct fallback UI, not a crash.

## Eval harness (`eval/`)
- **Golden set**: curated by the human, not generated by Claude Code
  as a bulk task. Leave the folder empty.
- **Expected output**: hand-verified `ResumeData` JSON per CV in
  `eval/expected/`, treated as ground truth for scoring.
- **What gets measured**: field-level accuracy (did extraction match
  expected?), latency per CV, estimated cost per CV, and — the
  headline comparison — Haiku-only vs Haiku-with-escalation accuracy
  and cost. This last number is what justifies the router design in
  stage 7; it should be a real measured percentage in the README, not
  an assumed one.
- **Caching**: `run-eval.ts` caches LLM responses to disk keyed by
  input hash, so re-running the harness during development doesn't
  re-spend budget on unchanged inputs.
- **Run cadence**: run the full harness twice — once mid-build to
  tune prompts/thresholds, once at the end for the final numbers that
  go in the README. Not on every commit; it costs real money.

## What "coverage" means here
No specific percentage target. The bar is: every deterministic
decision point in the pipeline (match level thresholds, page/char
limits, escalation triggers, fallback regex patterns) has at least
one test exercising it directly, not just through an end-to-end path.
